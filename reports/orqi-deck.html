A single binary that boots with your orq.ai workspace already wired in: 46 MCP tools, 21 skills, the TonyBot prompt, three subagents. Working proof of concept, built this week.

The gap

Skills that assume a setup nobody did

  • Today

    TonyBot lives in the sidebar. Our skills ship through assistant-plugins and assume the user has already added the orq MCP server to their coding agent, with the right key, in the right workspace.

  • But debugging happens in a terminal

    Next to the repo that produced the failing trace. The sidebar can read the trace; it cannot read the code, or write the fix.

  • Precedent

    Raindrop ships workshop. OpenRouter ships ori. One branded binary, opinionated about one platform, installed with one command.

What we built

Distribution is the feature

  • The orq workspace, in the box
    All 46 MCP tools wrapped as native agent tools. pi ships no MCP support by design — we bridge it, and new orq tools appear without a code change.
    src/mcp.ts
  • Our skills, pre-installed
    14 from assistant-plugins (pinned to the commit the orq CLI pins) plus the 7 TonyBot skills from the design plan. No plugin install step.
    skills/ × 21
  • One credential, one provider
    Models route through the orq AI Router — the workspace's own 133 enabled models, and nothing else. Same key serves the tools and the LLM.
    src/model.ts
What it looks like

Two modes, no setup

$ orqi "why did customer-support fail today?" $ orqi # full TUI ▞▚ orqi (aka TonyBot) v0.1.0 ▚▞ openai/gpt-5.6-terra · orq-research · 46 tools · 21 skills · 133 models ~/work/customer-support-agent Ask me to: investigate a failing agent · check workspace health · cut cost · build evaluators · explain the platform.

Fullscreen TUI — composer pinned to the bottom, transcript scrolling on its own. It is a full coding agent, so it also has read / bash / edit / write: it can pull the trace and the code that produced it, then propose the patch. That is the thing the sidebar cannot do.

Architecture

One process, ~700 lines

Two things we deliberately did not reimplement: auth (the orq CLI owns login, workspaces, refresh — we shell out) and router wiring (ported from that CLI's launch pi path, so the two stay honest with each other). Ships as one file: bun run dist → cross-compiled tarballs, ~25 MB.

Findings

Three things worth acting on

MCP tools/list hangs
1 in 3
1.3s · 120s timeout · 0.4s
Models in picker, unfiltered
1410 → 133
40 providers → 1
  • The MCP server stalls on initialize and tools/list — no error, just a hang. Not auth: the same token succeeds on retry. Worked around with retries and a cached catalogue; deserves a server-side fix.
  • Model errors can be invisible. A rate-limited turn returns an empty assistant message — it streams as silence. Anything embedding pi needs to check stopReason.
Decision needed

Is this a product or a demo?

The POC works end to end. Do we invest in shipping it — install script, cross-compiled binaries, a home in an orq repo — or keep it as an internal research tool?

Shipping means owning a distribution channel and a support surface. Keeping it internal means the skills stay dependent on each user configuring MCP correctly, which is the gap we set out to test.

A — Ship it: install script + binaries B — Internal tool, dogfood first C — Fold the learnings back into the sidebar
If we continue

On deck

  • Tool allowlist — all 46 schemas ship in every request today.
  • A model per subagent: cheap for doc lookups, strong for root-cause analysis.
  • Signing and notarization — unsigned binaries are quarantined by macOS, so today sharing means a tarball plus an xattr note.
  • An install script (curl … | bash), the way workshop and ori do it.
  • Dogfood on real incidents and measure it with our own evaluators.
