orqi — TonyBot as a dedicated CLI

TL;DR — orqi is a single binary that embeds the pi coding agent and boots with the orq.ai workspace already wired in: 46 MCP tools, 21 skills, the TonyBot system prompt, three subagents, and the orq AI Router as its only model provider. No claude mcp add, no plugin install, no per-user setup — orq auth login and you are talking to your workspace. It compiles to one 71 MB file with the skills baked in, and runs fullscreen in the terminal. Same shape as Raindrop's workshop and OpenRouter's ori (which is also pi underneath).

Why a CLI at all

TonyBot already exists as a hub prompt and a sidebar agent. The gap this POC probes is the other half of the workflow: engineers debugging agents live in a terminal, next to the repo that produced the failing trace. The design plan's Milestone 4 called for a coding-agent wrapper; this is that, taken one step further — instead of shipping skills that assume the orq MCP server is configured, the tools and skills ship inside the binary.

The bet: distribution is the feature. A branded binary is one curl away from any laptop, and it cannot be misconfigured, because there is nothing to configure.

What it can do

Two modes. One-shot for scripting and CI, interactive TUI for actual debugging:

$ orqi "why did customer-support fail today?" # one-shot $ orqi # interactive TUI

Because it is a full pi session, it also has read, bash, edit and write — so it can read the trace and the code that produced it, then propose the patch. That combination is what the sidebar cannot do.

# root-cause a failing agent, span by span
orqi "list the failed traces on customer-support in the last 24h,
      then walk the worst one to the first upstream failure"

# tools it will reach for
orq_list_traces · orq_list_spans · orq_get_span · orq_get_agent
# cost and health questions
orqi "where is my spend going this month, by model?"
orqi "what changed in the workspace in the last 7 days?"

# tools
orq_get_analytics_overview · orq_query_analytics · orq_list_models

orqi "make an LLM judge for citation accuracy and
      run it against the agent-eval-samples dataset"

The boot path, step by step

Startup is five steps and about a second when the caches are warm. Each one is a single small module.

1 · Resolve a credential src/auth.ts › credentialCandidates

Two candidates, best first: ORQ_API_KEY from the environment, then the active-workspace token from the orq auth login session (~/.orq/sessions/default.json, read only after orq auth whoami has refreshed it). Login, workspace switching and token refresh are the orq CLI's job — orqi shells out rather than reimplementing any of it.

The candidates are not pre-probed. They are tried on the real MCP connection, so a 401 selects the next candidate while a server hang stays a server hang. An exported key that is stale or scoped to another workspace therefore falls back to the login session automatically — which is exactly what happens on the machine this was built on.

The active workspace is resolved here too, because it silently scopes every tool call. With a login session it is activeWorkspaceKey; with only an API key it comes from the key itself — orq keys are sk-orq-<jwt> whose payload carries workspace_id. That yields a UUID, so with no session to map it against the short id is shown rather than a guessed name. It is highlighted in the header and pinned to the footer as orq:<workspace>, and re-rendered after /workspace <key>.

2 · Wrap the orq MCP tools src/mcp.ts › connectOrqTools

pi ships no MCP support by design ("4 tools, no sub-agents, no permissions"), so each of the 46 tools on https://api.orq.ai/v2/mcp is wrapped as a native pi tool named orq_<name>. The MCP JSON schema is passed straight through with Type.Unsafe, which keeps the bridge indifferent to the server's catalogue — new orq tools appear without a code change.

The catalogue is cached for 24h in ~/.orqi/agent/tool-catalogue.json, with retries and a stale-cache fallback, because the server hangs often enough to matter (see Gotchas).

Results render as a one-line summary — 23 items · 6.0 KB — via a custom renderResult; ctrl+o expands to pretty-printed JSON. The model still receives the full payload. This is necessary because the server answers with a single unbroken line, so pi's built-in 10-line result preview never trims anything and a list of agents wraps into a screenful.

3 · Register the router as the only provider src/model.ts › createOrqModelRuntime

A TypeScript port of what orq launch pi does in the orq CLI (cli/custom/launch/pi.go): fetch the workspace's enabled models from GET /v2/models, keep the ones that are chat models with tool calling, and write a models.json declaring the AI Router as one openai-completions provider called orq. The key never lands in the file — pi expands $ORQ_API_KEY at request time.

onlyOrq() then wraps the runtime in a Proxy that filters every model read to provider === "orq". Without it, any HF or Anthropic key in the environment adds its own catalogue to the picker: 1410 models across 40 providers on this laptop, versus 133 from the workspace. One filter covers the /model picker, the footer and ctrl+P cycling, because they all read through those methods.

4 · Load skills and the system prompt src/main.ts › createAgentSessionServices

21 skills ship in the binary: 14 from orq-ai/assistant-plugins (vendored at the commit the orq CLI pins) and the 7 TonyBot skills from the design plan. They are handed to pi as additionalSkillPaths, so no bespoke SKILL.md parser exists here.

Ambient discovery is off by default. pi would otherwise pick up every skill installed on the machine — 105 of them here — which both swamps the prompt and makes orqi behave differently per user. ORQI_LOCAL_SKILLS=1 re-enables it.

5 · Start the session src/main.ts

With an argument, it is a one-shot: stream the answer, print it, exit non-zero if the turn ended in a provider error (an empty assistant message would otherwise read as success). With no argument, it builds an AgentSessionRuntime and hands it to pi's InteractiveMode — the real TUI, with streaming, tool rendering and slash commands.

The TUI runs in pi's fullscreen mode (0.84+), so the composer stays pinned to the bottom of the terminal and the transcript scrolls on its own — ORQI_TUI=regular falls back to inline rendering. pi's startup header, changelog panel and update notice are all silenced (they advertise pi, and pi update does not apply to this binary); in their place a compact orq header is appended as a session entry, which is what makes it survive the alternate screen.

Architecture

One process. Everything the agent needs is in memory before the first token.

Roughly 700 lines of TypeScript across eight files. Two things are deliberately not reimplemented: authentication (the orq CLI owns it) and router wiring (ported from that CLI's launch pi path, so the two stay honest with each other).

Why the subagents are in-process

Every published pi subagent extension spawns the pi binary as a child process. A child started that way would inherit none of this: the MCP tools live in this process's memory, wired at startup. So the subagent tool is ~50 lines that call createAgentSession recursively with a specialist prompt and a filtered slice of the same tool array.

Three types, mirroring the design plan's pillars — investigator (traces, spans, agents), analyst (analytics, models), docs (search_docs only). Each gets a fresh context window, which is the point: walking a 40-span trace should not consume the main conversation.

★
Because subagents are ordinary sessions, giving each one its own model is a one-line change — a cheap model for the docs lookup, a strong one for root-cause analysis. That kind of heterogeneous routing is clumsy with subprocess delegation, and it is the obvious next experiment.

bun test                  # 4 checks
# embeds skills/themes/prompt, then compiles
bun run build

Gotchas worth knowing

  • The orq MCP server intermittently hangs. Measured over three identical tools/list calls: 1.3 s, timeout at 120 s, 0.4 s. It affects initialize too. This is not auth — the same token succeeds on retry, and real auth failures return 401 immediately. Worked around with 20 s timeouts, three attempts on a fresh connection, and a cached catalogue; it is still worth a server-side fix.
  • An exported ORQ_API_KEY can be silently wrong. The one on this machine returns "API key is not valid for this workspace". orqi falls through to the login session rather than failing, and the startup line always says which credential won.
  • Model errors used to vanish. A rate-limited turn comes back as an assistant message with stopReason: "error" and empty content, which streams as silence. Both the one-shot path and the subagent tool now surface errorMessage explicitly.
  • Workspaces have their own router limits. One workspace here caps at 50 requests/day; switching into it mid-session turns every prompt into a 429.
  • A bare binary sent over Slack is dead on arrival. It is only ad-hoc signed, never notarized, so macOS attaches com.apple.quarantine and SIGKILLs it — the recipient sees zsh: killed ./orqi and "orqi is damaged". Ship the .tar.gz instead: the flag lands on the archive, tar -xzf does not propagate it, and the executable bit survives. Apple Silicon and Intel need different builds.
  • All 46 tool schemas ship in every request. Fine for a POC, but an allowlist matched to the system prompt's tool table is the obvious first optimisation.

FAQ

Why pi and not Claude Code or a plain SDK loop?
pi is explicitly built for embedding: createAgentSession gives the full agent loop in-process, and its TUI, session management, compaction and slash commands come along for free. The orq CLI already knows how to launch it (orq launch pi), so the router wiring was a port rather than a design problem.
Does this replace the sidebar TonyBot?
No — it is the coding-agent surface of the same product. The sidebar has the platform UI around it; orqi has the repo, the shell and file editing around it. The skills and system prompt are shared, which is the point of vendoring them rather than rewriting.
How do new orq tools reach the CLI?
Automatically. The tool list comes from the MCP server at runtime and schemas pass through untouched; a new tool appears after the 24h cache expires, or immediately with ORQI_REFRESH_TOOLS=1.
How do skill updates reach it?
Today: re-copy from orq-ai/assistant-plugins and rebuild — they are vendored at a pinned commit, deliberately, so a bad upstream push cannot reach users unreviewed. That mirrors how the orq CLI pins the same plugin bundle.
What would it take to ship this?
Cross-compilation targets and an install script (bun build --compile --target=…), a tool allowlist to cut context, and a decision on the name — orqi avoids colliding with the existing orq CLI it shells out to.
